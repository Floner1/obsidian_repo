**1. apps.py**

```
Say why the runserver localhost patch has to stay

The monkeypatch in ready() looks like a stray local workaround, so the next
person tidying up will delete it. It is not dead. The machine it was written
for still forces HTTPS on 127.0.0.1 but not on localhost, and nobody ever
found which layer does it. Removing it breaks that dev loop with a symptom
pointing nowhere near this file.

The comment also says what the real change is: make it conditional, not
delete it.

Comment only. Nothing runs differently.
```

**2. reservation.html**

```
Send the email with the code when the discount field loses focus

validate_discount_code started failing closed without an email when the
binding check went in. The on-blur handler here still posted only the code,
so the inline check answered "enter the email address you are booking with"
every time, whatever the guest had typed.

It now sends $('#email').val().trim() alongside the code.

Confirmed against the dev server. A code posted alone still fails closed. The
same code with the address it was issued to comes back valid at 10%. With a
different address it comes back refused.
```

**5. Maintenance log**

```
Build the room maintenance log the schema has been waiting for

room_maintenance_logs has been in the schema since v10 with a status CHECK of
open/in_progress/resolved, a resolved_at and foreign keys to rooms and users,
and README.md line 226 has listed it as a working feature the whole time.
Nothing in the app ever read or wrote it.

Scope agreed before any of this was written. The room modal gets a textarea
under the condition buttons. Setting a room Out of Order with something typed
in it writes an open log row against that room, attributed to request.user.
Rooms with open issues carry a wrench badge and a count on their card, and
the modal lists them with a Resolve button.

Resolving deliberately leaves the room out of order. Staff still return it to
service with Empty Clean or Empty Dirty, so _display_status keeps one driver
rather than quietly gaining a second one in this table. in_progress stays
unused because nothing drives it.

The model is unmanaged like everything else in data/, and 0009 follows 0005:
CreateModel, managed False, no RunSQL. sqlmigrate prints a no-op. Unlike 0005
the two foreign keys are in the migration, so makemigrations does not come
back later wanting an AddField.

The log row is written after room.save(), not before. The status guard can
still refuse the click with a 409, and an open issue against a room that
never went offline is worse than no record at all.

Descriptions are capped at 1000 characters and refused above it rather than
truncated. The text reaches the modal through json_script and lands via
textContent, so a description containing markup renders as text.

log_id is screened with isdecimal, not isdigit. isdigit is true for
superscripts like the one in 10², which int() then refuses, turning a bad
request into a 500. Review caught that after the tests were green, so there
is now a test posting one.

Seventeen tests. Also driven against the dev server end to end, including the
escaping and the three bad log_id forms.
```
```
Let a broken occupied room be put back into service

Out of Order outranks the assignment in the derivation, so marking an occupied
room broken has always been allowed, and the maintenance log flow encourages
it. Getting the room back afterwards was the stuck part. Empty Clean and Empty
Dirty both wrote reservation_status to vacant, the derivation then correctly
returned occupied because the guest is still in the room, and the guard
compared that against the vacant the button had asked for and refused with a
409 blaming the booking. Neither button could ever clear the fault.

A clearing click on a room an assignment still holds is a maintenance write
rather than an occupancy one. It means the fault is fixed, not that the guest
has gone. So it now writes housekeeping only, clean or dirty depending on which
button was clicked, and leaves reservation_status alone. _display_status goes
back to reading occupancy off the assignment, the same as it already does for
every other occupied room.

None of this changes what "the assignment wins" means. The assignment still
decides occupancy. It just stops blocking a write that was never about
occupancy in the first place.

The no-assignment path is untouched. With no booking to defer to, the click
still owns both fields, and there is a regression test pinning that.

The assignment lookup moved above the status writes, because whether a click
counts as a maintenance clear depends on the room as it stands rather than as
it is about to be. The comment on the refusal branch claiming clearing clicks
never reach it was only true when no assignment was involved, so it now says
which case takes the exemption and which one has already had housekeeping
reset.

RoomMaintenanceLog also joins __all__ in data/models/__init__.py, matching
every other model there. Nothing behaves differently, it was already reachable
through the direct data.models.hotel import.

Five tests: the reported case on both clearing buttons, the no-assignment path,
Occupied still refused on a broken assigned room so the carve-out stays narrow,
and the whole loop with a guest in the room, a fault logged, resolved, and the
room back in service still showing occupied.
```

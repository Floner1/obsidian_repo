this was what was done for the hotel:

Keep a checked-in guest in the room they already have

allocate_room treats an assignment as stale once the booking's dates or room type stop matching it. It then releases the room and searches the pool for a replacement. Releasing first is deliberate and stays: the availability query excludes rooms with an overlapping active assignment, so without it the booking's own row would hide the room it is sitting in. What was missing is any preference for that room once it is back in the pool. random.choice picked from every free room of the type, so a guest kept the room they were in with probability 1/N. On a pending or confirmed booking that costs nothing. On a checked_in one it means extending a stay moves a guest who is asleep in the room, and staff get no say in it, because the only thing they clicked was a date. So allocate_room now keeps the room the booking already holds whenever it is still free for the new range, whatever the booking's status. The random pick only runs when that room is gone. When it is gone and the booking is checked_in, the extension is refused with an error naming the guest and the room. allocate_room already runs inside a transaction the caller rolls back, so the booking keeps the dates it had. Pending and confirmed still re-roll, since nobody has moved in yet. One more thing on the same path. update_room_status wrote reserved for every allocation, and deallocate_room had just marked the room vacant on its way past, so a checked-in guest's room came out of a date change reading reserved with someone in it. It now writes occupied when the booking is checked_in. Two tests. random.choice is patched to hand back the other room in the first one, so keeping the right room cannot pass by luck.

Send the booking confirmation after the caller's transaction, not inside it

create_reservation calls queue_booking_confirmation below its own atomic() block, under a comment saying the send happens after the transaction commits. Read on its own, the code matches the comment. get_reservation is what breaks it. It wraps the whole create_reservation call in a second atomic() so the milestone count and the booking it gates land under one lock on the guest's user row. That demotes the inner block to a savepoint, and the send then runs with the outer transaction still open and the lock still held. The send is synchronous SMTP. EMAIL_TIMEOUT is 15 seconds and queue_booking_confirmation posts twice, guest then admin, so a slow or dead mail server can sit on a row lock for half a minute. Two bookings from the same guest serialise behind it for a reason that has nothing to do with the milestone check the lock was added for. on_commit callbacks are measured against the outermost atomic block, so registering the send there defers it to the real commit when a caller has one open and runs it inline when nobody does. Both callers get what the comment already promised. The try/except moved inside the callback. Once the transaction has committed there is no caller left to raise to, and the failure was already logged into email_queue rather than surfaced. The lock is untouched. Two tests: one reproducing get_reservation's shape around the service, one posting a real booking through the view and checking the connection is out of its atomic block by the time the send fires.
